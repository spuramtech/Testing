Key findings

Issues surfaced against the live app during automation, not gaps in the test code. Ranked by what a reviewer should look at first.

HighValidation failures are silent — no visible error message anywhere in the wizard

Blank mandatory fields, a duplicate Loan Name/Code, and every boundary violation (Interest Rate Min > Max, Loan Amount Min > Max, Tenure From > To) are all correctly rejected — the wizard simply declines to advance or add a row — but at no point does any toast, inline message, or highlighted field tell the user why. A user gets no feedback at all when a submission is silently blocked.

Fix: add an inline error message or toast for each of these rejection paths so users understand why Next/Add did nothing.

MediumMandatory/Required proof-type checkboxes have no accessible name

On the Identification Documents tab, every checkbox in the PAN/Identification/Financial/Bank Proof tables renders as <label for="idproofmandate1"></label> — the label element exists and is correctly wired to its input's id, but contains no text. A screen-reader user hears an unlabeled checkbox for every single proof-type row.

Fix: add visually-hidden label text ("Mandatory - PAN CARD", "Required - PAN CARD", etc.) to each checkbox's label element.

MediumDuplicate id / formcontrolname attributes across the wizard

Found on three separate tabs: the EMI / No EMI radios (Installment Due Date tab) share one literal id="loaninstalmentmode" on both inputs; the Interest Rate Type select and the day-of-month field appear twice in the DOM with the same formcontrolname; and the Penal Interest radios reuse id="inlineRadio1" / id="due" across visible and hidden variants. Duplicate ids are invalid HTML and undermine both label association and any JavaScript/automation that targets elements by id.

Fix: give every form control a unique id/formcontrolname, including hidden/alternate variants of the same field.

InfoCompany Code / Branch Code are read-only, contrary to the original spec

The brief described Company Code and Branch Code as free-text, "highlighted/required styling" inputs. In the live app both render as read-only <label> display fields, auto-populated by the app and not editable by the user at all.

InfoThe "Loans Configuration" screen has no dedicated list page — it's the Loan Creation tab

The brief described a separate list screen (search box, Export PDF/Excel, standalone grid) ahead of the wizard. In the live app, navigating Loans › Loan Configuration › Loans Configuration lands directly on the 5-tab wizard with the existing-loans grid embedded under Tab 1. That embedded grid has no search box and no Export buttons — confirmed by inspecting the live DOM, not assumed.

InfoAdded-configuration-row grid state appears session-scoped, not draft-scoped

The Loan Configuration tab's "added rows" grid should start empty for every brand-new Loan (confirmed empty in isolated verification). But when running the full suite back-to-back, the grid's starting row count was observed as non-zero (5) at the start of several tests despite each opening a fresh "+ New" wizard — suggesting the grid's state may be tied to the logged-in account/session rather than reset per Loan draft. Worth a manual check by a human tester logging in twice in a row and opening "+ New" each time.

Root cause & recommended fix for failed tests

Two distinct failure patterns account for all 7 failures.

Pattern ALoan Type dropdown timeout — "Fixed % numeric input", "Clear resets Loan Configuration tab fields"

The Loan Type <select> element is found in the DOM instantly, but never becomes visible/enabled within the 15s action timeout. This happens on the first interaction after opening a new wizard — pointing to the live demo server being slow to finish rendering/hydrating the Angular form under repeated automated load, not a locator or logic bug (the same locator works reliably in the majority of runs).

Fix: increase actionTimeout from 15s to 30-45s for this step; add an explicit waitFor({ state: 'visible', timeout: 30000 }) on the Loan Type dropdown right after clickNew(); add a short stabilization pause (networkidle or ~500ms) after opening the wizard, since its initial paint appears to race with Angular's async data load.

Pattern BConfiguration grid row-count inconsistency — 5 "Add row" tests

The before row count is read as 5 even though each test opens a brand-new "+ New" wizard, and after clicking Add the row count polls back as 0 and never converges within 10s. This points to two compounding issues: the "added configuration rows" grid may not be scoped per-draft on the backend (state carried on the shared session/account), and the DataTable's redraw is slower than the poll timeout under server load.

Fix: isolate state per test (clear localStorage/sessionStorage/cookies or hard-reload before each test); increase the row-count poll timeout to ~20s; re-verify the baseline by reading before twice before proceeding; ideally run this suite against a dedicated/isolated test environment rather than the shared live demo.
