Key findings

Nothing here failed a test — every item below is a real app behavior the suite had to be corrected against after an initial wrong assumption, surfaced through repeated live verification rather than guessed from the spec. All four are now the source of truth in Pre-Closure prompt.md and pages/PreClosurePage.js.

Spec correctionDelete has no confirmation step

The original brief assumed a confirm/cancel prompt on delete, matching most CRUD grids in this app. Verified live: clicking the trash icon removes the row immediately — no dialog, no native window.confirm, nothing to cancel.

Action: spec and deleteRowByLoanName() both updated to the immediate-delete behavior. Worth a product conversation — every sibling screen in Loan Configuration deletes the same way, so this is either deliberate or a gap across the whole module.

Navigation topologySidebar "Pre-closure" opens the form, not the list

Clicking Pre-closure in the left nav lands directly on the New/Edit form (route PreclosureMaster). The grid everyone thinks of as the "Pre-closure screen" is a second route, PreclosureView, reached only via the "View" control in the form's top-right corner — itself a plain clickable <span>, not a link.

Action: navigateToPreClosure() and navigateToPreClosureList() are now two distinct page-object methods so every test states which one it means.

UI stateThe submit button reads "Save" or "Update" depending on mode

Same control, same position, different label: "Save" when creating, "Update" when editing an existing row. A locator pinned to the literal text "Save" silently stops matching the moment a test opens a row for edit.

Action: the submit-button locator now matches /^(Save|Update)$/.

TimingLoan Name options load asynchronously after Loan Type changes

The Loan Name dropdown is empty until an Angular call populates it in response to the Loan Type selection. Selecting Loan Name immediately after Loan Type — the natural thing to automate — sometimes fires before the options exist.

Action: fillForm() now waits for the Loan Name <select> to gain more than its placeholder option before selecting from it.

passedkeystroke-level filtering blocks non-numeric characters that a raw DOM write does notinfo

The percentage field's appnumbersonly directive only listens for real keydown events. Setting its value with .fill() (a direct DOM write) let a bare "−1" through untouched; switching every negative/injection test to .pressSequentially() — simulated real typing — showed the directive does correctly strip the character. The gap is automation-method, not app behavior, but worth flagging: any client-side filter here is bypassable by anything that sets the DOM value directly rather than typing.
