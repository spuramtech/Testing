Key findings

Issues surfaced against the live app, not gaps in the test code. Ranked by what a reviewer should look at first.

CriticalLedger & Applicable dropdowns have no accessible label

axe-core flags the "Type Of Ledger" and "Applicable" ng-select inputs as critical: <input role="combobox" type="text"> with no aria-label, no associated <label>, and no title/placeholder for assistive tech. A screen-reader user cannot tell what either field is for.

Fix: add aria-label="Type Of Ledger" / aria-label="Applicable" to the two ng-select components, or wrap them in a labelled <label for>.

HighSidebar never collapses on mobile — "+ New" is unreachable

At a 390px viewport the left navigation stays permanently expanded and pushes the grid and "+ New" button off-screen with no hamburger/collapse control. The Charge screen is effectively unusable on a phone-width viewport.

Fix: add a responsive breakpoint that collapses the sidebar to an icon rail or off-canvas drawer below ~768px.

MediumDelete has no confirmation step, contrary to spec

The brief states deleting a Charge "must prompt for confirmation." In the live app the trash icon deletes the row immediately — verified live: the row disappears with no dialog and no way to cancel. deleteCharge() now tolerates both behaviors, but the "cancelling delete keeps the row" regression test can never pass until a real confirmation step exists.

Fix: either add a confirm/cancel dialog on delete, or update the spec to reflect the immediate-delete behavior as intentional.

InfoReal dropdown values differ from the spec's placeholder examples

Type Of Ledger is actually Income / Liability (spec said Income/Expense). Applicable is actually five values — Pre Loan(FI), Upto Disbusement, Before Close, After Close, Any Time — not the two the spec implied. Both are now the source of truth in constants/chargeConstants.js and the equivalence-partitioning tests below.

HighRoot cause found and partially fixed: the API lives on a different subdomain

A live DevTools-equivalent network capture on 2026‑09‑01 found the real API host is demonbfc-api.finsta.co.in — not demonbfc.finsta.co.in/api as every .env* file had it configured. That single misconfiguration was the root cause of every earlier API failure. API_BASE_URL in all four env files and the confirmed endpoints in api/chargeApi.js (fetchChargeList → GET /loans/masters/ChargesMaster/GetChargesName, login → POST /login with the real pUserName/pPassword payload shape) have been corrected and re-verified: the API suite now completes in ~11s instead of timing out, and 4/9 tests pass (up from 3/9).

5 tests still fail, for a new and different reason: calling POST /login directly (outside a real browser) gets 404 from the real ASP.NET/Kestrel backend even when Origin/Referer headers are set to match the app exactly — the identical call succeeds inside an actual browser session. This points to a WAF/bot-protection layer fingerprinting real browser traffic, not a wrong path. Because the API-level login can't get a token this way, the list/schema/unauthenticated/token tests that depend on it can't be meaningfully validated via direct HTTP calls.

createCharge/updateCharge/deleteCharge/fetchChargeById were not captured (doing so would create/mutate a live record) — they're a best-effort guess following the confirmed ChargesMaster controller naming convention and are explicitly documented as unconfirmed in api/chargeApi.js.

Next step: confirm with the backend team whether direct API-client login is supported at all (an API key / service-account flow may be the intended path instead of replaying the browser's session login), and capture the real create/update/delete request URLs via DevTools when there's time to click Save once on the live app.

InfoSession lives in sessionStorage — framework built around it

This server keeps its login token in sessionStorage, not cookies or localStorage, so Playwright's storageState() reuse trick silently fails, and the server cannot handle a fresh login on every test. The suite instead logs in once per worker and reuses that authenticated page (fixtures/pageFixtures.js) — this cut the full-suite run time from ~30 minutes to ~4.
