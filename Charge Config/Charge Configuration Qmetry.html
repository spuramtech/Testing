Key findings

Issues surfaced by exercising the live app, not gaps in the test code. Ranked by what a reviewer should look at first. The screen under test is the "Add / Config" Charge Configuration form: Loan Type → Loan Name → Charge Name header, an in-place Charge Amount panel toggled between "Dependent on loan range" and "Not Dependent on loan range", GST Type, and Effective From.

MediumCharge Name dropdown filters already-configured charges inconsistently

For Personal Loan → Personal Loan, two Charge/Fee rows are already configured: Processing Charges and Processing Fee. Re-opening the Charge Name dropdown shows Processing Fee excluded (as expected, to prevent duplicates) but Processing Charges still listed as selectable. The two already-configured charges are treated inconsistently by the same dropdown.

Fix: confirm the intended rule with product — either both already-configured Charge/Fee names should be excluded (duplicate prevention client-side) or neither should be, with the server rejecting true duplicates on Add and Save. Currently the client-side behavior looks arbitrary.

InfoAmount fields format with thousands separators as you type

Minimum/Maximum Charge Amount (and the Range panel's Min/Max Loan Value) apply live currency formatting — entering 5000 renders as 5,000 in the field. This is expected UI behavior (an appmycurrencyformatter directive), not a defect; noted because it affects how any automation or manual tester should assert field values.

InfoNumeric-only input filtering is keystroke-driven

The amount fields use an appnumbersonly directive that filters characters as they are typed (keydown-level). Programmatically setting a field's value in one shot bypasses that filter entirely — automation must type character-by-character to exercise the real validation path, and any future manual paste-based entry should be spot-checked separately since paste may bypass the same filter.

InfoSeveral dropdowns and the configured-charges grid load asynchronously

Loan Name (after Loan Type), Charge Name and the configured-charges DataTable (after Loan Name) all repopulate via AJAX rather than being present in the initial DOM. Automation that selects a value and immediately inspects a dependent control without waiting for the follow-up fetch will intermittently see stale/empty state — this shape of race is worth keeping in mind for any future manual test scripts as well ("select, then wait for the grid to redraw" rather than "select, then assert").

InfoDemo server showed timeout flakiness under repeated automated runs

After several consecutive full-suite executions in the same session (~150+ logins), a handful of runs hit page.goto / navigation timeouts (30s) that were not reproducible on a fresh run. This reads as environment/server load rather than an application defect, but is worth knowing if CI later runs this suite back-to-back frequently.

How to reproduce

cd "Charge Config"
npm install
npx playwright install chromium

npm test -- --grep-invert "@destructive" --workers=1   # this report's scope
npm run test:destructive                                 # Add Charge + Submit, mutates the live grid — run deliberately
npm run report                                            # open the HTML report from the last run

Serial execution (--workers=1) is intentional: running this suite with Playwright's default parallel workers against this demo server produced a cascade of unrelated timeouts (each worker triggers its own fresh login), so every run in this report was captured serially.
